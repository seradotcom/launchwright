# R42 — Frozen editorial Markdown to editable PPTX and real PDF

Launchwright R42 adds a **bounded private deck export** from one already reviewed, immutable Markdown candidate. The result contains:

- an **editable PowerPoint** (.pptx): each title, paragraph, and bullet is a native text element;
- an actual multi-page **PDF** for reading/review, created independently from the same source/layout model;
- a private JSON receipt recording the candidate SHA, original Markdown SHA-256, page count and full output byte hashes.

R42 does not create marketing claims, substitute an external product capture, add approval or publish. It is the first verified technical part of the original DECK_PDF master profile. Human design review, accessibility assessment, customer brand/style requirements, support for complex content and customer production acceptance remain separate.

## Input contract and limits

A Launchwright deliverable must be rendered to a Markdown artifact through the canonical Native SDK dispatcher and **frozen into a Candidate**. The Candidate must be fresh, byte-pinned, authorized for a private draft and separately receive a human **APPROVED_EDITORIAL** review. Source/content revisions invalidate the plan. If technical verification is not PASS, the operator must independently acknowledge that the output remains technically UNKNOWN.

This first renderer supports:

- One first-level title heading, optionally followed by up to 5 provenance lines that are a Markdown blockquote at the beginning.
- Up to 7 second-level section headings (each becomes a content slide).
- At most 5 short plain paragraphs/bullets per section, 108 characters per item.
- One title, one slide per source section, and one source/review slide: 2–9 pages.
- Text is measured using real PDF Helvetica font widths before either format is generated. If it cannot fit without clipping, the command **fails closed**. Exact approved source words are preserved, not rewritten, summarized, or guessed.

Unsupported: tables, code blocks, arbitrary nested Markdown, images, rich media, long unbreakable text, emojis or glyphs not supported by the current PDF WinAnsi fonts. These need future format/renderer work, **not replacement characters or silent truncation**. The output uses a neutral dark visual style because no private customer branding or licensed font is provided. There are no bundled font files.

## Step 1: immutable private plan (no file writes except the plan itself)

```sh
node scripts/deck-pdf.mjs plan \
  --state /private/launchwright-workspace \
  --candidate CANDIDATE_ID \
  --artifact ARTIFACT_ID \
  --out /private/deck-pdf-plan.json \
  --acknowledge-draft \
  --acknowledge-unverified
```

The plan contains only reviewed identifiers, SHA-256 digests, page count and private authority metadata — not the source text itself. It is created with an exclusive 0600 file on POSIX, never overwritten.

## Step 2: independently confirm plan and export to private directory

Create an empty directory with private owner permissions (0700 on POSIX), then:

```sh
node scripts/deck-pdf.mjs export \
  --state /private/launchwright-workspace \
  --plan /private/deck-pdf-plan.json \
  --out-dir /private/deck-output \
  --confirm-plan FULL_64_CHARACTER_PLAN_SHA256 \
  --confirm-candidate FULL_64_CHARACTER_CANDIDATE_SHA256 \
  --acknowledge-private-export
```

Two real document files and a source-bound receipt appear in the **operator-chosen local directory only**. No external network request, GitHub PR, public package or Semwright Platform publication occurs.

Both formats are constructed from one font-measured layout. Their page count is verified against the approved plan; the PPTX is parsed back as valid OOXML with editable slide text, and the PDF is loaded as a real readable PDF. Packaging timestamps are normalized so the exact frozen source can be reproduced byte-for-byte across reruns. Pre-existing files are verified against the exact regenerated bytes **before writing anything**. Incomplete output from a process failure can be recovered by rerunning the **same plan**, but modified user files and symlink directories are never clobbered.

## Genuine owned E2E and visual QA

The separate selective [deck workflow](../.github/workflows/deck-pdf.yml) runs Node 24 from an exact Git commit in a disposable Linux runner. It:

1. Executes R42 tests against real Native SDK-backed, owned synthetic candidate/review state.
2. Generates a real editable PPTX and PDF using exactly that owned synthetic source.
3. Reopens the zipped PPTX and PDF and checks their page/model/byte digests.
4. Extracts PDF text and renders all pages through Poppler.
5. Independently opens the PPTX in LibreOffice/Impress and exports/render-checks it to a second PDF.
6. Retains the generated PPTX, both PDFs, page images and receipt as a GitHub Actions artifact.

The visual inspection compares actual slides, not an assistant-drawn mockup. **A synthetic render PASS is not a customer's branding/rights/accessibility, Slide deck design quality approval or Platform Publish acceptance.** Exact results and source SHAs belong to their recorded CI runs only.

## Supply-chain boundary

R42 pins pptxgenjs 4.0.0, pdf-lib 1.17.1 and JSZip 3.10.2. The text-only PPTX renderer does not use image parsing; a forced override pins image-size to patched 2.0.4 because the compatible 1.x dependency carried a high-severity infinite-loop advisory. The override will require revalidation before adding source-image support. CI runs npm audit and never downloads private fonts or executes a customer project script.

**Bounded CI acceptance:** Exact owned synthetic Node24/independent renderer or Chromium results and source SHAs are recorded in [evidence/r42/ci-runs.json](../evidence/r42/ci-runs.json). This is not customer, privacy, publisher-account or Platform authority.
